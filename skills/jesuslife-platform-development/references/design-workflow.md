# 설계 절차

대상 문서와 현재 제약을 확인하고 문제·사용자·성공 조건·비범위를 먼저 정한다. 제품 경계, 사용자 흐름(실패·취소·복구 포함), 데이터 원본 소유권과 공개 범위를 정리한다.
API 계약 초안에는 요청/응답, 버전, 인증·권한, 오류, 재시도·멱등성, 하위호환성을 담는다. 후보 데이터 모델은 초안으로 표시하고 실제 DB에 적용하지 않는다.
대안을 기존 구조 재사용, 사용자 기록 보호, 구현 비용, 되돌리기 가능성으로 비교한다. ADR에는 맥락·결정 후보·대안·영향·미결정 사항을 기록하고 로드맵에는 의존성과 검증 조건을 붙인다.
CHGO 후보는 근거·출처·상태·기존 ID 연결 후보를 기록하며 정본 승인이나 Canonical ID 발급을 대신하지 않는다.
신학 문구, Canonical ID, 개인정보 공유, DB 구조, 인증 경계는 AUTHOR_REVIEW_REQUIRED로 분류하고 검토할 구체적 초안과 영향 범위를 제시한다. 사람의 승인이 필요한 부분만 대기한다. 설계 요청만으로 앱 코드·DB·운영 설정을 변경하지 않는다.
복합 요청은 승인된 설계와 인수 조건을 개발 단계로 전달한다.

질문·사전 안내·승인과 외부 보조 스킬 사용은 [공통 규칙](common-rules.md)을 따른다. 이 파일은 설계 절차의 단일 원본이며 설계 스킬의 자료 안내에서 참조한다.
